# ADR-0003：删除语义

**状态**：已锁定（v1）；2026-11 修订（决策 2「按现状硬删、改文档承认」）：产物性数据由"软删留墓碑"改为硬删，已并入下文。

## 背景

"删除"至少有三类：

* **结构性数据**：名单、场次、选手、机器、题目。它们是骨架，删掉后引用方要么跟着没、要么悬空。
* **产物性数据**：选手代码、下发资产，是**发生过的事**的记录。
* **批量解绑**：删一份名单会连带解绑绑在其条目上的所有机器，不可逆且**静默**。

考场现实是"选手确实交过，只是后来被清了"，成绩复核时这份历史比干净的数据重要。

## 决定

**结构性数据**：

- 硬删，**确认方式是输入名称**（`confirm` 必须逐字等于 `player_no` / `slug` / `name` / `hostname`），**服务端**校验。
- **删有机器绑着的名单** → 拒绝，409 `roster_in_use`，给出台数、前几个考号和出路（先到「机器配对」改派或解绑）。
- **删单条名单条目** → 允许（这个人走了），响应如实说明副作用：解除了 1 台机器的配对，它下一轮心跳显示新配对码。
- **应用名单**时 `prune` 默认关；显式打开也**不删已有代码或成绩的选手**，并在结果里列出。
- **「默认名单」只是预设**，要落地必须显式点「按这份名单补人」。
- **手工录入的成绩永不被自动扫描覆盖**（"强制重扫"也不行）。

**产物性数据**（教师在管理端删除一律硬删）：

| 动作 | 行为 |
|---|---|
| 选手在机器上删掉 / 改名文件（扫描对账，`services/collect.py`） | **唯一的墓碑**：仅在 `scan_complete=true` 时给台账行置 `deleted_at`（界面叫"已消失"），行与内容保留；文件再出现或再上传时清掉并记 `file_restored` |
| 删一份代码（`DELETE /files/{id}`） | 硬删该行；内容无任何记录引用时一并删 blob。不要求 `confirm` |
| 清空代码台账（`POST /contests/{id}/files/clear`，`confirm` = 场次 slug） | `purge=false`（默认）只删"已消失"的行，`purge=true` 连现存的一起删（机器还在报的下一轮会回来）；无人引用的 blob 一并删 |
| 删资产（`DELETE /assets/{id}`） | 硬删资产行，下发任务与逐选手进度随外键级联删除；`Asset` 没有 `deleted_at` 列；已落到机器上的文件不撤回 |
| 删选手 / 删场次 | 结构性硬删，代码台账与成绩级联删除 |

- blob 一律在**提交之后**按引用回收（含删资产 / 选手 / 场次的级联），提交失败不会留下指向已删 blob 的行。
- `source/<场次>/<考号>/` 里已落盘的文件**任何删除动作都不碰**（落盘是硬链接，blob 删了副本仍在）；选手在机器上删掉的文件也留在那里。
- `?include_deleted=` 只控制"已消失"行。列表 API 默认 `false`、界面勾「含已删除」才显示；导出接口默认 `true`，与界面「导出」一致。

## 后果

- 打名称不会被连续操作的肌肉记忆点掉，"是否确定"弹窗会。
- 删名单被挡时教师拿到的是出路而非错误码。
- `test_setting_the_default_roster_does_not_touch_players` 钉住默认名单语义：设/改默认名单后 `player_count` 仍为 0，显式应用后才变 1；否则有人把 `PATCH` 改成自动补人也不会有地方变红。
- "这个人确实交过"的证据落在两处：扫描对账的"已消失"行（导出默认带上）与 `source/` 里从不被删的落盘副本。
- **代价**：教师删掉的代码 / 资产**找不回来**（行与无人引用的 blob 都没了）；要留证据就先导出再清空。单删一份代码不要求确认，因为它只删一行、至多连带一份 blob。

## 被否掉的替代方案

* **场次直接引用名单**：改名单会连带改掉历史场次的参赛者（成绩矩阵列、代码目录、下发目标、成绩外键）。名单是**模板，不是引用**。
* **把 `player_no` 冗余到机器上，删名单照旧能用**：学年末机器要换一批学生，旧绑定留着更糟；诉求是不静默、不意外地解绑，而非永不解绑。
* **删名单"允许但警告"**：不可逆的批量解绑，"确定吗"会被点掉；端点原说明只写"不动任何场次的选手"，没提机器被解绑，正是静默事故的成因。
* **`prune` 默认打开**：名单调整是常事，连带删提交是不可逆且不报错的事故。
* **`PATCH` 场次默认名单时自动补人**：悄悄改了语义；界面出路是给**动作**（「按这份名单补人」），不是一句解释。
* **产物性数据软删留墓碑**（v1 原定，从未实现）：管理端删代码的真实用途（清掉"选手早删了"的已消失行、去掉误收文件，见 `delete_source_file` docstring）要的都是"这一行真的没了"，再打墓碑等于清墓碑要清出第二层；补上它要同时改台账、列表、导出、清空、资产表结构与前端，而复核证据已有两份不依赖它的来源。
* **英文 pydantic 422 结构当错误体**（同源问题）：见 [`../reference/api-conventions.md`](../reference/api-conventions.md) §3。
