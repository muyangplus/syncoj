# ADR-0003：删除语义

**状态**：已锁定（v1）

## 背景

这个系统里的"删除"至少有三类完全不同的东西：

* **结构性数据** —— 名单、场次、选手、机器、题目。它们是别的数据的骨架，删掉之后
  引用它的那一堆东西要么跟着没了、要么悬空。
* **产物性数据** —— 选手的代码、下发的资产。它们是**发生过的事**的记录。
* **批量解绑** —— 删一份名单会连带把绑在那些条目上的机器全部解绑，这是不可逆的、
  而且是**静默**的。

考场现实是："选手确实交过，只是后来被清了"。成绩复核时这份历史比干净的数据重要。

## 决定

- **结构性数据** → 硬删除，而且**确认方式是输入名称**（`confirm` 必须逐字等于
  `player_no` / `slug` / `name` / `hostname`），校验在**服务端**做，不只是前端弹窗。
- **产物性数据**（代码文件 / 下发资产）→ 软删除留墓碑，`?include_deleted=true` 可见；
  导出**默认包含已删除的代码**。
- **删名单里有机器绑着的条目** → **拒绝**，返回 409 `roster_in_use`，并给出台数、
  前几个考号、以及出路（先去「机器配对」改派或解绑）。
- **删单条名单条目** → **允许**（那本来就是"这个人走了"），但响应里要如实说明副作用：
  解除了 1 台机器的配对，它下一轮心跳会显示新的配对码。
- **应用名单**时 `prune` 默认关闭；**即使显式打开，已经有代码或成绩的选手也一个都
  不删**，并在结果里列出来。
- **手工录入的成绩永不被自动扫描覆盖**（连"强制重扫"也不行）。
- **「默认名单」只是预设**，不是"选好就自动补人"；要落地必须显式点「按这份名单补人」。

## 后果

- 用"是否确定"的弹窗在连续操作里会被手指肌肉记忆点掉，打名称不会。
- 删名单被挡住之后，教师拿到的是一个**出路**而不是一个错误码。选拒绝而不是
  "允许但警告"，理由与上一条相同：这是不可逆的**批量**解绑。
- `test_setting_the_default_roster_does_not_touch_players` 把这个语义钉住：
  设/改默认名单之后 `player_count` 必须还是 0，显式应用之后才变 1。这条测试挡住的是
  有人为了消掉"为什么没补人"的疑惑而把 `PATCH` 改成自动补人 —— 那时语义变了而
  没有任何地方会红。
- 软删除让"导出"这件事的默认值变成一个必须想清楚的决定：默认**包含**已删除的代码。

## 被否掉的替代方案与理由

* **场次直接引用名单（而不是复制一份）**。它会让"改一下名单"连带改掉
  历史场次的参赛者 —— 那时成绩矩阵的列、代码目录、下发目标、既有成绩的外键全都会
  跟着动。名单是**模板，不是引用**。
* **把绑定信息冗余到机器上（`player_no` 冗余存一份），删名单也照旧能用**。
  学年结束时教室的机器要换一批学生，旧绑定留着反而更糟。真正的诉求是
  **不要静默地、意外地解绑**，不是"永远不许解绑"。
* **删名单时"允许但警告"**。这是不可逆的批量解绑，一句"确定吗"在连续操作里会被
  点掉；而端点原来的说明只写了"不动任何场次的选手"（对场次确实没动，但机器被解绑了，
  那句话没提）—— 这正是它变成静默事故的原因。
* **`prune` 默认打开**。名单调整是常事，连同参赛者的提交一起删掉是不可逆的事故，
  而且它**不报错**。
* **硬删产物性数据**。成绩复核时需要"这个人确实交过"的证据。
* **422 那样的英文 pydantic 结构当错误体**（与删除语义同源）。见
  [`../reference/api-conventions.md`](../reference/api-conventions.md) §3。
* **`PATCH` 场次设置默认名单时自动补人**。见上：它把语义悄悄改了，而没有任何地方
  会红。界面上的出路是给一个**动作**（「按这份名单补人」），不是给一句解释。
