# ADR-0003：删除语义

**状态**：已锁定（v1）；**2026-11 修订**：产物性数据改为承认硬删，见文末「修订（2026-11）」。
下面「决定 / 后果 / 被否掉的替代方案」保留 v1 原文作为历史，被修订取代的条目已就地标出。

## 背景

这个系统里的"删除"至少有三类完全不同的东西：

* **结构性数据** —— 名单、场次、选手、机器、题目。它们是别的数据的骨架，删掉之后
  引用它的那一堆东西要么跟着没了、要么悬空。
* **产物性数据** —— 选手的代码、下发的资产。它们是**发生过的事**的记录。
* **批量解绑** —— 删一份名单会连带把绑在那些条目上的机器全部解绑，这是不可逆的、
  而且是**静默**的。

考场现实是："选手确实交过，只是后来被清了"。成绩复核时这份历史比干净的数据重要。

## 决定

- **结构性数据** → 硬删除，而且**确认方式是输入名称**（`confirm` 必须逐字等于
  `player_no` / `slug` / `name` / `hostname`），校验在**服务端**做，不只是前端弹窗。
- ~~**产物性数据**（代码文件 / 下发资产）→ 软删除留墓碑，`?include_deleted=true` 可见；
  导出**默认包含已删除的代码**。~~
  **已被修订取代**：代码从来没有按这条实现过，现状是硬删（见文末）。
- **删名单里有机器绑着的条目** → **拒绝**，返回 409 `roster_in_use`，并给出台数、
  前几个考号、以及出路（先去「机器配对」改派或解绑）。
- **删单条名单条目** → **允许**（那本来就是"这个人走了"），但响应里要如实说明副作用：
  解除了 1 台机器的配对，它下一轮心跳会显示新的配对码。
- **应用名单**时 `prune` 默认关闭；**即使显式打开，已经有代码或成绩的选手也一个都
  不删**，并在结果里列出来。
- **手工录入的成绩永不被自动扫描覆盖**（连"强制重扫"也不行）。
- **「默认名单」只是预设**，不是"选好就自动补人"；要落地必须显式点「按这份名单补人」。

## 后果

- 用"是否确定"的弹窗在连续操作里会被手指肌肉记忆点掉，打名称不会。
- 删名单被挡住之后，教师拿到的是一个**出路**而不是一个错误码。选拒绝而不是
  "允许但警告"，理由与上一条相同：这是不可逆的**批量**解绑。
- `test_setting_the_default_roster_does_not_touch_players` 把这个语义钉住：
  设/改默认名单之后 `player_count` 必须还是 0，显式应用之后才变 1。这条测试挡住的是
  有人为了消掉"为什么没补人"的疑惑而把 `PATCH` 改成自动补人 —— 那时语义变了而
  没有任何地方会红。
- ~~软删除让"导出"这件事的默认值变成一个必须想清楚的决定：默认**包含**已删除的代码。~~
  （已被修订取代。现在"已删除"只剩扫描对账打的"已消失"标记，界面上的导出默认带上它们。）

## 被否掉的替代方案与理由

* **场次直接引用名单（而不是复制一份）**。它会让"改一下名单"连带改掉
  历史场次的参赛者 —— 那时成绩矩阵的列、代码目录、下发目标、既有成绩的外键全都会
  跟着动。名单是**模板，不是引用**。
* **把绑定信息冗余到机器上（`player_no` 冗余存一份），删名单也照旧能用**。
  学年结束时教室的机器要换一批学生，旧绑定留着反而更糟。真正的诉求是
  **不要静默地、意外地解绑**，不是"永远不许解绑"。
* **删名单时"允许但警告"**。这是不可逆的批量解绑，一句"确定吗"在连续操作里会被
  点掉；而端点原来的说明只写了"不动任何场次的选手"（对场次确实没动，但机器被解绑了，
  那句话没提）—— 这正是它变成静默事故的原因。
* **`prune` 默认打开**。名单调整是常事，连同参赛者的提交一起删掉是不可逆的事故，
  而且它**不报错**。
* ~~**硬删产物性数据**。成绩复核时需要"这个人确实交过"的证据。~~
  （v1 否掉的正是现状；2026-11 修订改为接受它，理由与代价见下。）
* **422 那样的英文 pydantic 结构当错误体**（与删除语义同源）。见
  [`../reference/api-conventions.md`](../reference/api-conventions.md) §3。
* **`PATCH` 场次设置默认名单时自动补人**。见上：它把语义悄悄改了，而没有任何地方
  会红。界面上的出路是给一个**动作**（「按这份名单补人」），不是给一句解释。

## 修订（2026-11）：产物性数据按现状硬删

**状态**：已锁定（决策 2：「按现状硬删、改文档承认」）。

### 背景：v1 的"软删留墓碑"从来没有实现

2026-11 审计对照 `server/syncoj_server/api/admin.py` 发现，教师在管理端发起的删除
**全部是硬删**，墓碑只存在于另一条路径上：

| 动作 | 实际行为 |
|---|---|
| 选手在机器上删掉 / 改名一个文件（扫描对账，`services/collect.py`） | **唯一的墓碑**：只在 `scan_complete=true` 时给台账行置 `deleted_at`（界面上叫"已消失"），行与内容都留着；文件再出现或再上传时清掉 `deleted_at`，记一条 `file_restored` |
| 删一份代码（`DELETE /files/{id}`） | 硬删这一行；内容**没有任何记录再引用**时把 blob 一并删掉。不要求 `confirm` |
| 清空代码台账（`POST /contests/{id}/files/clear`，`confirm` = 场次 slug） | 硬删：`purge=false`（默认）只删已经"已消失"的行，`purge=true` 连还在的一起删（机器还在报的下一轮会回来）。无人引用的 blob 一并删掉 |
| 删资产（`DELETE /assets/{id}`） | 硬删资产行，下发任务与逐选手进度跟着外键级联删掉。`Asset` 表**根本没有** `deleted_at` 列；已经落到机器上的文件不撤回 |
| 删选手 / 删场次 | 结构性硬删，代码台账与成绩跟着级联删掉 |

另外两条与"删"有关、但不归管理端删除管的事实：

* `source/<场次>/<考号>/` 里已经落盘的文件**任何删除动作都不碰**（落盘是硬链接，
  blob 被删之后这份副本照样在）。选手在机器上删掉的文件也一样留在那里。
* `?include_deleted=` 看到的只是扫描对账打的"已消失"行。API 默认 `false`
  （列表与导出都是）；界面上「导出」按钮显式传 `true`，所以从界面导出**默认带上**
  已消失的文件，台账列表默认不显示、勾「含已删除」才显示。

### 决定

* **承认现状**：代码文件与资产被教师删除就是硬删，文档不再写"墓碑"。
* **"已消失"这层墓碑保留**：它来自选手机器上的事实（文件不见了），不是教师的动作，
  "这个人确实交过"的证据就落在这里，也仍然是导出默认带上的东西。
* 结构性数据"硬删 + 输入名称确认"不变。

### 为什么接受硬删，而不是补上墓碑

* 管理端删代码的两种真实用途 —— 清掉"选手早删了、服务端还留着已消失记录"的行，
  以及把误收的文件从归档里去掉（见 `delete_source_file` 的 docstring）—— 要的都是
  "这一行真的没了"。在它们上面再打一层墓碑，等于"清墓碑"要清出第二层墓碑。
* 补墓碑要同时改台账、列表、导出、清空、资产表结构与前端，而 v1 期望的复核证据已经有
  两份不依赖它的来源：已消失标记，和 `source/` 里从不被删的落盘副本。

### 代价

* 教师删掉的代码 / 资产**从系统里找不回来**（行没了，无人引用的 blob 也没了）。
  要留证据，就在清空之前先导出归档。
* 清空要把场次 slug 打一遍；单删一份代码不要求确认 —— 它删的只是一行、可能连带一份 blob。

### 还没做（代码侧，`docs/design/08-milestones-and-open.md` §10.5 阶段 3）

* blob 回收现在在**提交之前**（同一个会话里 `flush` 之后就删文件）：提交失败会留下
  指向已删 blob 的行。要改为提交后按引用计数回收。
* `delete_asset` / `delete_player` / `delete_contest` 级联删掉的行**不回收 blob**，
  孤儿内容一直留在 `blobs/` 里。
