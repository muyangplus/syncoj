# ADR-0006：验收不许拿自己人替代

**状态**：已锁定（v1）

## 背景

这套东西里有两处"自己验自己"的诱惑：

1. **升级包的信任锚**。密钥目录 `.key/` 里有私钥和公钥，构建时读一次、验收时读一次
   —— 看起来最省事。但那对文件是否配套、公钥有没有**真的内嵌进包**、
   签名对象到底是"包的字节"还是"shasum 的十六进制串"，这三件事在"读同一个目录"
   的验收里全都不会暴露。
2. **手写的密码学代码**。Agent 零依赖（[ADR-0001](ADR-0001-tech-stack-and-dependencies.md)），
   所以 RSA 验签是手写的。自签自验永远能过，**证明不了任何事**。

这两处的共同点：验证者与被验证者共用同一份实现或同一个假设，于是错误会**同时**
出现在两边，测试恒绿。

## 决定

**验收链路里不许出现"我们自己再实现一遍"的中间结果。**

- 升级那条链路用测试**整条**跑一遍：构建 → 签发 → 铺开 → 从**面向 Agent 的那个
  接口**下载 → 交给 **Agent 自己的** `verify_bundle` 验签验摘要 → `safe_extract_tar`
  解开。全程用目标机上会跑的那份代码。
- 信任锚取的是**包里内嵌的那份**，不是密钥目录里再读一次。
- RSA 手写实现的正确性证据来自 **openssl 交叉验证**：我们的签名与 openssl 逐字节
  相同；openssl 的签名我们的代码能验。签名对象是 **sha256 的十六进制字符串**，
  而不是包本身的字节。
- 校验是**严格**的：整体重建 `EM` 后比较，不做"解析出 hash 再比对"。
- 服务端的路径安全校验**独立实现一遍**（`agent/syncoj_agent/safepath.py` 是另一份），
  两者一致性由契约测试中的 `test_path_validation_parity` 守住。
- 前端类型绝不手写，从 OpenAPI 生成。

## 后果

`server/tests/test_release_build.py` 里最要紧的那一条**不检查任何中间结果**，
它只把整条链跑一遍。于是这三件事任何一件错，它都会红：

* `.key/` 那对文件是否配套；
* 公钥有没有真的内嵌进去；
* 签名对象是不是 sha256 的十六进制串。

openssl 交叉验证还额外要求 **openssl 1.1.1 与 3.0 两种默认输出格式都能读** ——
只对一种格式验通，等于把"验签失败"的锅甩给对方的版本。

## 被否掉的替代方案与理由

* **验收时从 `.key/` 再读一次公钥**。那样"公钥有没有内嵌进包"这件事永远不会被测到，
  而它错的表现是：界面上发版成功、铺开成功、然后**所有机器一动不动** ——
  这是整个功能里最难查的一种故障。
* **自己写一遍验签来做测试**（测试里再实现一次 `pow(sig, e, n)`）。测试与被测代码
  会犯同一个错，而"两边一致"被当成"两边都对"。
* **用 Ed25519**（原定方案）。硬阻塞：**Python 3.8 标准库不含任何非对称签名原语**
  （`hashlib` 只有摘要，没有椭圆曲线），而 Agent 必须零依赖。要用它就得引入
  `cryptography`/`pynacl`，直接违背零依赖约束。改用 RSA-2048 + PKCS#1 v1.5 之后
  纯 Python 的实现量从"完整的 Curve25519 点运算"降到"一次 `pow(sig, 65537, n)`
  加字节比较"，手写风险低得多（公钥指数只有 17 位，且不涉及曲线算术）。
* **宽松校验（解析出 hash 就认为通过）**。PKCS#1 v1.5 历史上的伪造攻击
  （Bleichenbacher 2006 等）**全部**源于宽松校验。
* **密钥生成也在纯 Python 里做**。Miller-Rabin 与随机素数搜索是好写但**极易写错**的
  密码学代码，而这是一次性管理操作 —— shell 到 `openssl` 完全可接受。
* **信任锚改用配置里的路径**。见第一条：那样就把"包里那份"换成了"服务端手边那份"，
  两者不同步时机器一律拒收，而现场只看到"升级没生效"。
