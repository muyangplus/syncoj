# ADR-0011：zip 密码用 ZipCrypto 而不是 AES

**状态**：已锁定（v1）

## 背景

教师会想"这一场的题面换个密码"，而"回自己机器上重新打一个包、再上传一遍"纯属仪式。
所以服务端支持**就地给 zip 打密码 / 改密码**（`services/zipcrypto.py`）。

那就要选加密算法。学生的打开方式是 **Archive Manager**（GNOME file-roller）——
它解得开 ZipCrypto，遇到 AES 会直接说打不开。

还有一层：**密码本身怎么送到学生手里**。如果密码要经过系统另存一份，
服务端就多存了一份明文，而它本来只需要在教师手上。

## 决定

- 用 **ZipCrypto（PKZIP 传统加密）**，不是 AES。
- 口径只能是：**挡得住随手翻看，挡不住有心人**。绝不写成"安全加密"。
- 密码按 UTF-8 编码；**不支持 ZIP64**（>4GB / >65535 条目，超出给 400）。
- **库里没有单独的密码字段**：密码只存在于自动生成/更新的那份 `password.txt`
  文本资产里，教师随时能读回来、也能像别的资产一样下发。
- `password.txt` 是**单件语义**：改一次密码就更新同一条，而不是每次新建。
- **审计事件里不写密码** —— 写了就等于服务端多存一份明文。
- 读那一半**仍然走标准库**：好让"我们写出去的包能不能读回来"由独立实现判定。

## 后果

- 服务端对压缩格式保持**零第三方依赖**（只用标准库 + 上面那份自写的 ZipCrypto
  写实现），也换来"落盘字节与教师手里那份逐字节相同"这个可验证的性质。
- 改密码会让这个包**重新排队给还没下完的机器**（同一个 asset id 换掉
  `sha256`/`size`，已完成的下发目标重排回 `PENDING`、续传偏移清零）；
  **已经落到机器上的那份不会跟着变**。
- `password.txt` 自己也是明文，所以它更适用于"别让人误点开看一眼"，
  而不是防住一个真的想看的人 —— 这一句必须跟着功能一起说出来，
  不然它会变成一句"我们加密了"的错觉。
- 与"在线改正文"共用同一套语义（改完重排下发目标），所以两个入口的行为一致。

## 被否掉的替代方案与理由

* **AES 加密**。更安全的是它，但**学生打不开** —— 而这份包的唯一用途就是给学生看。
  一个"更安全但打不开"的包等于没有下发。
* **加密但不说明口径**（不写"挡不住有心人"）。`password.txt` 是明文的，教师很容易
  误以为这是"保密"；把结论写清楚，才不会出现"用这套东西保护真不该泄的题"。
* **不在服务端就地改密码**，让教师回本机重新打包上传。那是纯粹的仪式，
  而且现场最容易发生的是"包里的密码和发下去的 `password.txt` 不一致"。
* **库里存一个密码字段**（改密码时就地更新）。那等于服务端多存一份明文，
  还会和 `password.txt` 形成两个真相；而它本来只需要在教师手上。
* **改密码时新建一份 `password.txt`**。改一次密码就多一条同名文件，列表上很快躺着
  几条，而教师没有依据判断哪份最新 —— 发错的那次学生看到的就是"密码不对"。
* **支持 ZIP64**。>4GB / >65535 条目的包在考场下发的场景里没有真实需求，
  而支持它会让那份自写的 ZipCrypto 写实现复杂一大截（引入 Zip64 扩展字段、
  数据描述符等）。超出直接给 400，比"支持但偶尔写坏"好。
* **审计里记下密码以便复盘**。那枚密码的价值只到"学生打开包"为止，把它抄进一份
  到处被导出、被翻看的日志里，是净亏。同一条纪律也管着远程卸载的令牌
  （见 [ADR-0012](ADR-0012-remote-uninstall-authorization.md)）。
