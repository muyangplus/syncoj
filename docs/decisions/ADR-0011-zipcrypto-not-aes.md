# ADR-0011：zip 密码用 ZipCrypto 而不是 AES

**状态**：已锁定（v1）

## 背景

教师会想给这一场的题面换密码，回本机重打包再上传没有意义，所以服务端支持**就地给 zip 打密码 / 改密码**（`services/zipcrypto.py`）。
学生用 **Archive Manager**（GNOME file-roller）打开：它解得开 ZipCrypto，遇到 AES 直接说打不开。
密码如何送到学生手里也要定：经系统另存一份等于服务端多一份明文，而它只需要在教师手上。

## 决定

- 用 **ZipCrypto（PKZIP 传统加密）**，不用 AES。
- 口径只能是**挡得住随手翻看，挡不住有心人**，绝不写成"安全加密"。
- 密码按 UTF-8；**不支持 ZIP64**（>4GB / >65535 条目回 400）。
- **库里没有密码字段**：密码只在自动生成/更新的 `password.txt` 文本资产里，教师可读回、可照常下发。
- `password.txt` **单件语义**：改密码更新同一条，不新建。
- **审计事件不写密码**。
- 读那一半**走标准库**，让"写出的包能否读回"由独立实现判定。

## 后果

- 压缩格式上**零第三方依赖**（标准库 + 自写的 ZipCrypto 写实现），落盘字节与教师手里那份逐字节相同。
- 改密码与"在线改正文"同一套语义：同一 asset id 换 `sha256`/`size`，已完成的下发目标重排回 `PENDING`、进度清零；**已落到机器上的旧包不会跟着变**，要等重新下发。
- `password.txt` 本身是明文，所以这只防"误点开看一眼"；这句必须随功能说出，否则会变成"已经加密了"的错觉。

## 被否掉的替代方案

* **AES**：更安全但**学生打不开**，而这个包的唯一用途就是给学生看。
* **加密但不说明口径**：教师易误以为能"保密"，拿它保护真不该泄的题。
* **不在服务端改密码、让教师重打包上传**：多一步手工，且最易出现"包里密码与发下去的 `password.txt` 不一致"。
* **库里存密码字段**：服务端多一份明文，还与 `password.txt` 形成两个真相。
* **每次改密码新建 `password.txt`**：列表堆着几条同名文件，教师分不清哪份最新，发错时学生看到"密码不对"。
* **支持 ZIP64**：考场下发没有真实需求，却让自写实现复杂一大截（Zip64 扩展字段、数据描述符）；直接 400 比"支持但偶尔写坏"好。
* **审计记密码以便复盘**：密码价值只到"学生打开包"为止，抄进到处被导出的日志是净亏；同一纪律也管远程卸载令牌（[ADR-0012](ADR-0012-remote-uninstall-authorization.md)）。
