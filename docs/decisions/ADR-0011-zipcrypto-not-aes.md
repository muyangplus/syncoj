# ADR-0011：zip 密码用 ZipCrypto 而不是 AES

**状态**：已锁定（v1）

## 背景

- 服务端支持**就地给 zip 打密码 / 改密码**（`services/zipcrypto.py`），教师无需回本机重打包上传。
- 学生用 **Archive Manager**（GNOME file-roller）打开：支持 ZipCrypto，不支持 AES。
- 须确定密码如何送到学生手里，且服务端不额外存明文。

## 决定

- 用 **ZipCrypto（PKZIP 传统加密）**，不用 AES。
- 口径：**挡随手翻看，不挡有心人**；不称"安全加密"。
- 密码按 UTF-8；**不支持 ZIP64**（>4GB / >65535 条目回 400）。
- **库里没有密码字段**：密码只在自动生成/更新的 `password.txt` 文本资产里，教师可读回、可照常下发。
- `password.txt` **单件语义**：改密码更新同一条，不新建。
- **审计事件不写密码**。
- 读那一半**走标准库**，让"写出的包能否读回"由独立实现判定。

## 后果

- 压缩格式上**零第三方依赖**（标准库 + 自写的 ZipCrypto 写实现），落盘字节与教师手里那份逐字节相同。
- 改密码与"在线改正文"同一套语义：同一 asset id 换 `sha256`/`size`，已完成的下发目标重排回 `PENDING`、进度清零；**已落到机器上的旧包不变**，重新下发后才更新。
- `password.txt` 本身是明文，只防"误点开看一眼"；该口径须随功能说明。

## 被否掉的替代方案

* **AES**：**学生打不开**。
* **加密但不说明口径**：教师会误以为能保密。
* **不在服务端改密码、让教师重打包上传**：多一步手工，易出现包内密码与 `password.txt` 不一致。
* **库里存密码字段**：多一份明文，且与 `password.txt` 形成两个来源。
* **每次改密码新建 `password.txt`**：列表出现多份同名文件，无法区分最新一份。
* **支持 ZIP64**：考场下发无此需求，自写实现复杂度大增（Zip64 扩展字段、数据描述符）。
* **审计记密码以便复盘**：日志会被导出，等于泄露；同一规则适用于远程卸载令牌（[ADR-0012](ADR-0012-remote-uninstall-authorization.md)）。
