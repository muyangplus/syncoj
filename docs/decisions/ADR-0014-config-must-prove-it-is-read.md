# ADR-0014：一个配置项必须有测试证明它真的被读到

**状态**：已锁定（v1）

## 背景

两个**看起来都配好了、其实没有**的坑，都是在这套东西里真实发生过的。

**第一个：`Settings.release_signing_key` 被声明了两遍。** 一次读
`SYNCOJ_RELEASE_KEY`、一次写死 `= None`。后一次静默覆盖前一次，于是那条环境变量
**从来没生效过** —— 而代码的写法与"配好了"完全一致。

**第一个坑在 513 项测试全绿的时候就在仓库里**，因为没有一条测试覆盖这个环境变量。

**第二个：测试会解析到开发者真实的 `.key/`。** `Settings()` 默认去仓库相对路径找
密钥目录，于是整套测试跑在"已配好私钥"的状态下 —— 那会把
"没有私钥就不提供升级"这条**最重要的安全默认值测反**：测试证明的是
"配好私钥时能升级"，而真正要守的是"没配私钥时升级整体关闭"。

## 决定

- **一个配置项必须有测试证明它真的被读到**，否则"看起来配好了"和"真的配好了"
  没有区别。`SYNCOJ_RELEASE_KEY` 现在有一条专门的用例，它断言的是那个环境变量的值
  **真的出现在 `Settings` 上**。
- 测试必须用 **`SYNCOJ_KEY_DIR`** 把密钥目录钉到临时目录。这条夹具是 **autouse** 的：
  忘了钉它，测试就会去碰开发者真实的密钥。
- 密钥的**门槛是"文件存在"**：这三条默认值全部是**有则生效、无则保持原样** ——
  没有私钥就照旧不提供任何升级，没有公钥就打出和今天一样的包，没有 `.key/` 目录就
  什么都不发生。
- 这三条**不能改成"无条件默认、缺失就启动失败"**：那会让一次干净的 `git clone`
  变成起不来的服务端，而"升级整体关闭"本来就是一个安全且可用的状态。
- **判据是"这个哈希在库里登记了没有"，不是"文件在不在"。** 密钥明文在 `.key/`、
  哈希在库里，而 `db reset` 只删库、不碰 `.key/` —— 所以"文件还在、哈希没了"
  这一态必然会出现，那时密钥在界面上看着好好的，注册却被判「密钥无效」。
  `init` 因此会**补登记**，但**已被吊销的绝不复活**。

## 后果

- 这两条都加了回归测试，而且测试写的是**性质**而不是当时那个 bug 的形状
  （"环境变量被读到"而不是"第 960 行不再写 `= None`"）。
- 结论就是标题这一句：**一个配置项必须有测试证明它真的被读到**。
  同一条道理也适用于新增的每一个环境变量与每一个 `Settings` 字段。
- `db reset` 与 `.key/` 的关系变成一条要记住的边界：
  `db reset` 只删库、不碰 `.key/`，所以"密钥文件还在、库里的哈希没了"是会出现的
  一态；`init` 会补登记，但吊销是有意动作，不该被一次 `init` 撤销。
- 生产部署请把密钥放到只有服务端账号读得到的地方，并用 `SYNCOJ_RELEASE_KEY` /
  `SYNCOJ_KEY_DIR` 指过去。

## 被否掉的替代方案与理由

* **靠"改配置的人记得同步改代码"**。这正是那条被声明两遍的 `release_signing_key`
  的下场：代码里两处、看起来都对，而生效的是后一处。
* **"测试覆盖率够高就没事"**。513 项全绿的时候这个 bug 就在仓库里。
  覆盖率衡量的是"代码被执行过"，而这里缺的是"这个配置**从外部进来**时行为正确"
  —— 是两种不同的性质。
* **不让测试去碰真实 `.key/`，靠"开发者自己注意"**。测试一旦解析到真实密钥目录，
  它证明的东西就反了（见背景）。这条必须由 autouse 夹具强制，
  而不能是一条写在文档里的提醒。
* **把"没有私钥"改成启动失败**（更"响亮"的错误）。那会让一次干净的 `git clone`
  变成起不来的服务端，而"升级整体关闭"本来就是一个安全且可用的状态。
* **`db reset` 连同 `.key/` 一起清掉**。那等于把一把可能还在别的机器上用的密钥
  无声地删掉；而"补登记但不复活已吊销的"这条行为是刻意区分的两种语义。
* **审计/日志里打一份配置快照**（"这样就能看出哪个键生效了"）。配置里含密钥与
  令牌，把它抄进日志与 [ADR-0011](ADR-0011-zipcrypto-not-aes.md)、
  [ADR-0012](ADR-0012-remote-uninstall-authorization.md) 那两条纪律冲突。
  正确的证据是"那个键的取值真的出现在 `Settings` 上"，那要一条测试，不是一份日志。
