# ADR-0014：一个配置项必须有测试证明它真的被读到

**状态**：已锁定（v1）

## 背景

两个"看起来配好了、其实没有"的真实坑：

1. **`Settings.release_signing_key` 被声明两遍**：一次读 `SYNCOJ_RELEASE_KEY`、一次写死 `= None`，后者静默覆盖前者，环境变量从未生效；当时全部测试仍绿，因为没有一条覆盖这个环境变量。
2. **测试解析到开发者真实的 `.key/`**：`Settings()` 默认找仓库相对路径的密钥目录，整套测试跑在"已配好私钥"状态下，把"没有私钥就不提供升级"这条最重要的安全默认值**测反**。

## 决定

- **配置项必须有测试证明它真的被读到**：`SYNCOJ_RELEASE_KEY` 有专门用例，断言其值**真的出现在 `Settings` 上**。新增的每个环境变量与 `Settings` 字段同理。
- 测试用 **autouse** 夹具以 **`SYNCOJ_KEY_DIR`** 把密钥目录钉到临时目录。
- 密钥门槛是**文件存在**：有则生效、无则保持原样（无私钥不提供升级、无公钥打不带公钥的包、无 `.key/` 什么都不发生）；**不改成缺失即启动失败**。
- 注册密钥判据是**哈希在库里登记了没有**，不是文件在不在：`db reset` 只删库、不碰 `.key/`，会出现"文件在、哈希没了"，界面看着正常而注册被判「密钥无效」。`init` 会**补登记**，但**已吊销的绝不复活**（吊销是有意动作）。

## 后果

- 回归测试写的是**性质**（"环境变量被读到"），不是那次 bug 的形状（"某行不再写 `= None`"）。
- 生产部署把密钥放到只有服务端账号可读的地方，用 `SYNCOJ_RELEASE_KEY` / `SYNCOJ_KEY_DIR` 指过去。

## 被否掉的替代方案

* **靠改配置的人记得同步改代码**：那条声明两遍的字段就是下场。
* **"覆盖率够高就没事"**：覆盖率衡量代码被执行过，这里缺的是"配置从外部进来时行为正确"。
* **靠开发者自己注意别碰真实 `.key/`**：一旦碰到，测试证明的东西就反了，必须由 autouse 夹具强制。
* **没有私钥就启动失败**：干净的 `git clone` 会起不来，而"升级整体关闭"本就安全可用。
* **`db reset` 连 `.key/` 一起清**：会无声删掉可能还在别处使用的密钥；"补登记但不复活已吊销的"是刻意区分的两种语义。
* **日志里打一份配置快照来证明生效**：配置含密钥与令牌，与 [ADR-0011](ADR-0011-zipcrypto-not-aes.md)、[ADR-0012](ADR-0012-remote-uninstall-authorization.md) 的纪律冲突；正确的证据是一条测试。
