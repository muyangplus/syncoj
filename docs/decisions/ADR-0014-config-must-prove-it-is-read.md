# ADR-0014：一个配置项必须有测试证明它真的被读到

**状态**：已锁定（v1）

## 背景

两次"配置看似生效、实际未生效"的故障：

1. **`Settings.release_signing_key` 被声明两遍**：一次读 `SYNCOJ_RELEASE_KEY`、一次写死 `= None`，后者静默覆盖前者，环境变量从未生效；无测试覆盖该环境变量，全部测试仍绿。
2. **测试解析到开发者真实的 `.key/`**：`Settings()` 默认找仓库相对路径的密钥目录，整套测试在"已配好私钥"状态下运行，"无私钥不提供升级"这一安全默认值被**测反**。

## 决定

- **配置项须有测试证明被读到**：`SYNCOJ_RELEASE_KEY` 有专门用例，断言其值**真的出现在 `Settings` 上**。新增的每个环境变量与 `Settings` 字段同理。
- 测试用 **autouse** 夹具以 **`SYNCOJ_KEY_DIR`** 把密钥目录钉到临时目录。
- 密钥门槛是**文件存在**：有则生效、无则保持原样（无私钥不提供升级、无公钥打不带公钥的包、无 `.key/` 什么都不发生）；**不改成缺失即启动失败**。
- 注册密钥判据是**哈希是否已在库里登记**，不看文件：`db reset` 只删库、不动 `.key/`，会出现"文件在、哈希没了"（注册报「密钥无效」）。`init` **补登记**，**已吊销的不恢复**。

## 后果

- 回归测试写的是**性质**（"环境变量被读到"），不是那次 bug 的形状（"某行不再写 `= None`"）。
- 生产部署把密钥放到仅服务端账号可读的目录，用 `SYNCOJ_RELEASE_KEY` / `SYNCOJ_KEY_DIR` 指定。

## 被否掉的替代方案

* **靠人工记得同步改代码**：即声明两遍故障的成因。
* **依赖覆盖率**：覆盖率只衡量代码被执行，不验证外部配置生效。
* **靠开发者自行避开真实 `.key/`**：一旦读到，测试结论相反；须由 autouse 夹具强制。
* **无私钥即启动失败**：干净的 `git clone` 会起不来；"升级整体关闭"是安全可用状态。
* **`db reset` 连 `.key/` 一起清**：会静默删掉可能仍在别处使用的密钥。
* **日志里打印配置快照证明生效**：配置含密钥与令牌，违反 [ADR-0011](ADR-0011-zipcrypto-not-aes.md)、[ADR-0012](ADR-0012-remote-uninstall-authorization.md) 的规则。
