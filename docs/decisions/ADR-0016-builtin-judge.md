# ADR-0016：自带评测走 judge_result/、独立评测机、借用 isolate

**状态**：已锁定（v1，2026-11）；扩充 [ADR-0001](ADR-0001-tech-stack-and-dependencies.md) 的"评测对接"一行（外部评测器那一路仍不触发评测）。

## 背景

SyncOJ 原本不触发评测：教师在 LemonLime / Arbiter（Qt 界面程序）里开评，SyncOJ 只扫描结果目录。需要一条不依赖它们的路：服务端自己编译、运行、比对。
选手代码是**不可信代码**，而服务端进程握着数据库、发布私钥与统一注册密钥。

## 决定

1. **结果写进 `judge_result/<场次>/<选手>/<题目>/result.json`**，由现有扫描器收进矩阵，不直接写 `judge_run` 表。
2. **评测在独立评测机进程里跑**（`syncoj-judge`，专用账号，可在另一台机器），经 HTTP 领任务、取内容、交结果；凭据是只能做这几件事的评测机令牌。
3. **沙箱借用 IOI 的 isolate**（调用，不链接）；另有只给开发自测的 `rlimit` 后端，结果标 `isolated: false`，以 root 运行时必须换账号。
4. 按题选外部评测器 / 自带评测；数据包上传时校验；考试进行中评测要显式确认。

## 后果

* 成绩矩阵、四种解析状态、"手工录入永不被覆盖"、导出全部原样生效；两种评测可在同一场按题混用。
* 评测机只用标准库，另一台机器 `pip install` 服务端包即得这条命令。
* 正式考试要多装 isolate（需要 root 与 cgroup 配置）。

## 被否掉的替代方案

* **直接写 `judge_run` 表**：要么绕过扫描器的规则（手工录入保护、四态），要么再写一遍；写文件让外部与自带评测天然一致。
* **评测放在服务端进程里**（线程池 / 子进程）：选手程序与私钥、数据库同账号，沙箱一有洞就丢整台服务端；评测跑满 CPU 还会拖慢收代码。
* **自研 unshare + seccomp + cgroup 沙箱**：这是安全边界，isolate 久经竞赛实战，自研的维护成本与出错代价不值得。
* **systemd-run 临时单元当沙箱**：隔离够用，但单次运行的 CPU 时间与峰值内存要从单元属性绕着取，精度与开销都不如 isolate（以后可补）。
