# ADR-0016：自带评测走 judge_result/、独立评测机、借用 isolate

**状态**：已锁定（v1，2026-11）；扩充 [ADR-0001](ADR-0001-tech-stack-and-dependencies.md) 的"评测对接"一行（外部评测器那一路仍不触发评测）。

## 背景

- 原有方式：教师在 LemonLime / Arbiter（Qt 界面程序）里开评，SyncOJ 只扫描结果目录。
- 需求：不依赖外部评测器，由 SyncOJ 编译、运行、比对。
- 约束：选手代码**不可信**；服务端进程持有数据库、发布私钥与统一注册密钥。

## 决定

1. **结果写进 `judge_result/<场次>/<选手>/<题目>/result.json`**，由现有扫描器收进矩阵，不直接写 `judge_run` 表。
2. **评测在独立评测机进程里跑**（`syncoj-judge`，专用账号，可在另一台机器），经 HTTP 领任务、取内容、交结果；凭据是只能做这几件事的评测机令牌。
3. **沙箱借用 IOI 的 isolate**（调用，不链接）；另有只给开发自测的 `rlimit` 后端，结果标 `isolated: false`，以 root 运行时必须换账号。
4. 按题选外部评测器 / 自带评测；数据包上传时校验；考试进行中评测须显式确认。管理端入口：侧栏「评测」页（题目评测设置、排任务与进度、评测机签发与吊销）。

## 后果

* 成绩矩阵、四种解析状态、"手工录入永不被覆盖"、导出全部原样生效；两种评测可在同一场按题混用。
* 评测机只用标准库；另一台机器 `pip install` 服务端包即得 `syncoj-judge`。
* 正式考试要多装 isolate（需要 root 与 cgroup 配置）。

## 被否掉的替代方案

* **直接写 `judge_run` 表**：须绕过或重写扫描器规则（手工录入保护、四态）。
* **评测放在服务端进程里**（线程池 / 子进程）：选手程序与私钥、数据库同账号，沙箱失守即丢失整台服务端；评测满载 CPU 拖慢收代码。
* **自研 unshare + seccomp + cgroup 沙箱**：安全边界自研的维护成本与出错代价过高；isolate 经竞赛长期使用。
* **systemd-run 临时单元当沙箱**：单次运行的 CPU 时间与峰值内存须从单元属性间接获取，精度与开销不如 isolate（可后补）。
