### 10.1 内置评测

**要做什么**：SyncOJ 自己编译、运行选手代码并对测试点判分，成绩直接进现有的成绩矩阵。
现在这一步在 SyncOJ 之外 —— SyncOJ 不触发评测，只收外部评测器（LemonLime / Arbiter）
写进 `judge_result/` 的结果（[`../reference/judge-result.md`](../reference/judge-result.md)）。

**这条与一条已锁定决策冲突**：`00-decisions.md` 里「评测对接 = 只投递 `source/` +
扫描结果目录回写成绩，**不触发评测**」是锁定的（连同
[`ADR-0001`](../decisions/ADR-0001-tech-stack-and-dependencies.md)）。落地前先按惯例改那条
决策、补一份 ADR 写明改动理由，不要先写代码。

**动手前要定的岔路**（每条都是选择题；未定就不动手）：

1. 评测跑在哪
   - A. 服务端本机：只有一处工具链、一处测试数据；代价是选手代码在服务端主机上执行，
     隔离与负载都压在服务端。
   - B. 派给机房里的 Agent：用机器上现成的编译器与空闲 CPU，服务端不扛评测；
     代价是逐机环境差异、占用考试机、结果要回传。
   - C. 按场次（或按题）二选一。
2. 隔离到什么程度
   - A. `setrlimit` + 独立运行账号：与 LemonLime 同级，不加新依赖。
   - B. cgroup v1（`systemd-run --scope`）：目标机的 systemd 245 支持，能管住整棵进程树。
   - C. nsjail / seccomp：隔离最强，但要往目标机上装新依赖。
3. 测试点数据从哪来
   - A. Web 上传 zip 进内容寻址的资产表：与现有下发同一条路（要不要与下发共用一张表另定）。
   - B. 指向服务端本地目录：与 `judge_result/` 同一种形态，教师自己放。
4. 谁触发
   - A. 交一次自动判一次。B. 教师点「评测」，含批量重测。C. 两者都要。
5. 语言范围：只 C++（NOI 的实际情况），还是加 C / Python（各要一套编译与限制）。
6. 判分范围：只逐点对错，还是也要 SPJ（特判）/ 交互题 / 子任务捆。

**落地时要一起改的**：

- `docs/design/04-server.md` §4.4 现在写的是"后台扫 `judge_result/`"；内置评测要在这条
  之外多一个成绩来源。
- 成绩矩阵的 `parse_status` 现在只有 `ok` / `unparsed` / `manual` / `missing`，要能区分
  「内置评测的」与「外部导入的」，否则重测与覆盖语义说不清。
- `judge_run` 现在只存到「选手 × 题」一个分数；内置评测要存测试点一级的结果、编译与
  运行错误，以及这条成绩是哪一版代码跑出来的（对得上 `source_file.revision`）。

### 10.2 客户机同步服务端的时区与时间

**要做什么**：让机房里的机器跟服务端的时区、时间对齐，并且这件事由服务端的**一个开关**
控制（关掉就什么都不做）。现在两边没有这层关系：服务端只是按 `SYNCOJ_TZ`（默认 UTC+8）
把时间**显示**给人看（[`04-server.md`](04-server.md)），机器上的时区与时钟由装机镜像
决定，跑久了各自漂。

**先看清两件事，否则会把这条做成"加一行 `date -s`"**：

* 改时区、改时钟都要 root，而常驻的 Agent 以普通账号跑。现有的提权通道只有远程卸载
  那一条 `sudo -n` + 一行**无参数** sudoers 规则
  （[`ADR-0012`](../decisions/ADR-0012-remote-uninstall-authorization.md)），另有 root
  一次性单元的先例 `syncoj-agent-enroll.service`
  （[`ADR-0009`](../decisions/ADR-0009-registration-is-a-root-unit.md)）。
* **跳变时钟会连累一批东西**：日志时间戳、`source_file.mtime`（回收台账按它记最后看到的
  版本）、评测结果扫描里"mtime 没变就跳过"那一层。考场里的常规做法是让机器跟 NTP 走，
  而那个源可以是服务端自己 —— 这一条是下面第 2 条的由来。

**动手前要定的岔路**（每条都是选择题，未定就不动手）：

1. 同步到哪一步
   - A. 只设时区（`timedatectl set-timezone`），不动时钟。
   - B. 时区 + 时钟都校。
   - C. 只比对偏差、把偏差显示在机器列表上，改不改由教师决定。
2. 时钟怎么校
   - A. 直接 `timedatectl set-time` / `date -s`：简单、立即；代价是时钟跳变。
   - B. 服务端做一个 NTP 源，客户端 `chrony` / `systemd-timesyncd` 指向它：平滑、标准；
     代价是服务端多一个常驻进程、客户机装机时要带配置。
   - C. B 优先、A 兜底：能配 NTP 就配，配不上的一次性校准。
3. 提权从哪来
   - A. 沿用 sudo 那条路，给安装器加一条只允许固定 `timedatectl` 命令的 sudoers 规则。
   - B. 加一个 root 的一次性单元，由服务端下指令时触发（照注册单元的样子）。
   - C. 不加提权通道 —— 那就只剩第 1 条的 C 类"只告警"可选。
4. 时区的名字从哪来
   - 现在的显示时区是**固定偏移**（`SYNCOJ_TZ=+08:00`），而 `set-timezone` 要的是 IANA
     名字（`Asia/Shanghai`）。要么加一个只给客户机用的时区名配置项，要么规定
     "`SYNCOJ_TZ` 写的是名字才下发、写成偏移就不下发"。
5. 开关的默认值与粒度
   - 默认**关**（考场里改时钟是高风险动作，要教师显式打开）还是默认开？
   - 整间机房一个开关（沿用「运行参数」的粒度），还是按机器？
6. 时间以谁为准
   - 服务端的系统时钟，还是服务端自己先跟上游 NTP 对齐之后的值？服务端也跑在一台
     普通机器上，它自己的钟同样可能不准。

**落地时要一起改的**：

- 「运行参数」现在只装三个整数秒（`services/runtime_settings.py`，整间机房粒度、非法值
  一律拒绝），加一个布尔开关要顺带想清楚它的界面与校验。
- `docs/reference/protocol.md` 的 tick 响应要加下发项（时区名 / 时间基准 / 偏差回执），
  `agent/tools/build_fixture.py` 的契约样本跟着重生成。
- 时区名若走配置项：`docs/reference/config-keys.md` 与 `CONFIG_POLICY_KEYS` 两处要同步
  （文档守卫逐键对账，漏一处就红）。
- 客户机时间**不参与**考试时间窗判定（那是服务端算的，选手页倒计时也取服务端时间）。
  这一点要写进协议文档，免得以后有人拿客户机时间做判断。

### 10.3 已知限制

（这一轮主动留下的取舍，不是缺陷。）

* 上传时若让服务端生成随机密码，密码只落在 `password.txt` 这份文本资产里；上传回执是
  资产体，不为它新增字段。教师想当场拿到密码就走「文件下发」页那条「打包成 zip」。
* 「运行参数」（空闲心跳 / 有活心跳 / 离线判定）是**整间机房**生效，没有按机器、
  按场次的粒度。
* 安装时换密钥留下的 `bootstrap.key.replaced-<时间戳>` 备份不清理。
* 同版本重装是就地替换，没有同版本回滚点。
* 诊断包**每台机器只留最新一份**：不存历史，也不提供原始 gzip 下载（要留旧包，就在
  管理端读到之后自己存出去）。按机器的 60 秒限速窗口在内存里，服务端重启即重置 ——
  代价只是可能多收一份。

### 10.4 被明确否决的想法

不再重新提案：

* **违规判定 / 迟到上传告警**。曾经设计成"结束时间之后的上传记一条 `late_upload`
  违规事件、点名到人"，用户明确否掉了：考试结束后文件本来就不该再同步，服务端直接
  **不收**就够了；再去判定"谁违规"是把一个技术状态变成了对人的指控，而网络抖动、
  机器卡顿都会让正常选手撞上这条线。现在到点只做两件事：拒收（409
  `contest_ended`）+ 把场次自动置为「已结束」（`contest_auto_closed`，info 级审计，
  不点名任何人）。
* **从题目模式推导"保存规则"给选手看**。服务端不知道每台机器的 `scan.roots` 与
  文件名前缀，推导出来的"把代码存到 X"很容易是错的，而一条错的操作指引比没有指引更
  坏。公告改成教师写一份 `NOTICE.md` 下发（../design/05-api-and-frontend.md §5.6）。
